## 三、变更记录

### 2026-11（构建阶段）

- **合并上游商品/订单域与钱包补全**：合并 PR#12（钱包：验证码、头像、实名加密、管理员调账）与 PR#13（窦源泽的商品域 + 完整订单状态机 + 数据库基线），订单模型由最小载体切换为完整订单域（出租者字段 owner→lessor、订单列表改 /orders?role=lessor、纠纷所属社区暂取物主已加入社区）；db 脚本新增 item.sql 与 migrations/，同步更新配置库索引与开发职责说明的 db 清单。
- **补齐演示种子数据**：`db/community-dispute-platform.sql` 新增社区成员、社区公告、入社申请、纠纷单（调解中 / 待仲裁）、调解留言、纠纷举证、举报等种子数据，打通「入社 → 审核 → 纠纷 → 调解 → 上报仲裁 → 举报处理」演示闭环。
- **合并上游前端**：合并 `upstream/main`（界面设计员林星的物品前端：登录退出、物品发布 / 编辑 / 删除 / 审核 / 状态筛选 / 详情交互等 12 个提交）。
- **解决合并冲突**：`AppTopbar.vue`（保留上游导航 + 退出登录，叠加「管理后台」入口）、`vite.config.js`（支持 `VITE_API_TARGET` 覆盖代理目标）。
- **修复中文乱码**：`db/*.sql` 增加 `SET NAMES utf8mb4;`，解决 `character_set_client=latin1` 导致的 UTF-8 中文双重编码问题。
- **完善部署与文档**：`README.md` 补充一键启动说明与测试账号；`scripts/start.sh` 修正前端端口；确认 `docker-compose.yml` 端口映射（前端 80 / 后端 8080 / MySQL 3307）。
- **一键部署与 CI 就绪**：前后端镜像构建 + `docker-compose.yml` + `.github/workflows/ci.yml`。
- **订单域最小载体**：新增 `backend/order/`（Order 实体 / Mapper / 服务 / 控制器）与 `db/order.sql`（`t_order` 建表 + 种子订单 + 押金冻结占位），`docker-compose.yml` 挂载订单脚本，为「发起纠纷」提供订单载体。
- **纠纷前端接通真实后端**：发起纠纷页接入订单下拉并自动带出社区 / 押金 / 租金；订单页新增「发起纠纷 / 举报」入口；平台管理内新增「调解工作台」「仲裁中心」标签页，列表点操作以弹窗方式查看详情并完成调解 / 上报仲裁 / 裁决划转。
- **调解成功解冻押金**：`DisputeService.resolve()` 补上调解成功后的押金解冻，全额退回租客（`unfreeze` 冻结池 → 可用余额）；订单状态恢复仍待订单域状态机。
- **纠纷双方均可发起**：发起纠纷表单按所选订单自动判断「我是租客/物主」——租客发起=对押金扣除有异议，物主发起=物品受损/缺件申请扣押金；去掉前端写死的 `renterId`，改由订单确定发起人/对方，「所属社区」改为订单只读带入。后端「发起人/租客/物主」三角色本就分离，无需改动。（本方案已由下一条「物主提出扣留押金」取代。）
- **物主提出扣留押金 → 租客回应（最终纠纷流程）**：推翻上一版「双方均可发起」，改为仅出租者（物主）可对订单提出扣留押金，租客回应「同意=立即划转和解（SETTLED）/ 不同意=进入社区调解（MEDIATING）」，之后仍走调解 → 上报仲裁 → 裁决。实现：`t_dispute` 新增 `withhold_amount`、`renter_note`；后端 `DisputeCreateRequest` 增扣留金额校验（0 < 扣留 ≤ 押金）、一个订单一生只能发起一次纠纷（含已和解/已调解/已裁决等终态均拦截重复发起）、新增 `POST /disputes/{id}/respond`（`RenterRespondRequest{agree,note}`）与 `DisputeService.respond()`；前端发起页改为仅物主订单可选的「提出扣留押金」表单，详情弹窗新增扣留金额/租客回应展示及「同意/不同意」操作，状态字典新增 `AWAITING_RENTER`/`SETTLED`。同时 `db/order.sql` 押金冻结占位调整（种子订单 101+102+201 押金 50+80+60=190；因 UC-D2 未落地，冻结基线由配置经理在演示库手工补齐）。
- **「一单一纠纷」与初始无纠纷演示**：前端「提出扣留押金」订单下拉对已发起过纠纷的订单标灰禁用（提示「已纠纷过，不可再发起」），无可选订单时给出空态提示；种子数据去掉预置纠纷及留言举证，三个种子订单初始均未发起纠纷，便于从零演示「提出 → 回应 → 调解 → 仲裁」闭环。
- **移除「租金减免」功能**：评审发现「租金减免」会在押金冻结池之外凭空造钱（退还租客的减免金额无资金来源，违反 BR-21 资金一致性，且与他组资金流接口难对齐），故整体删除。后端删除 `ArbitrateRequest.rentDiscount`、`DisputeArbitration.rentDiscount` 字段、`AwardResponse.rentRelief` 字段、`DisputeService.executeFundTransfer()` 的 `refund` 减免分支与 `arbitrate()`/`toAwardResponse()` 相关传参；`db/community-dispute-platform.sql` 的 `t_dispute_arbitration` 去掉 `rent_discount` 列（运行库同步 `ALTER TABLE ... DROP COLUMN rent_discount`）；前端 `ArbitrationView.vue`、`DisputeView.vue` 裁决书区去掉「租金减免」输入与展示，`mock/data.js` 去掉 `rentRelief` 字段。裁决资金流简化为「扣除押金划付出租者 + 剩余押金退回租客」两笔，闭环后押金池精确归零。
- **打通社区治理闭环（任命管理员 → 加入社区 → 管理员同意）**：排查发现社区三动作在界面上断链——① 平台管理员（PLATFORM_ADMIN）登录后导航只有「平台管理」，缺「社区管理」入口，导致其兼任社区管理员时无法在界面审核加入申请；② 「任命管理员」需手输用户 ID，且 `appointAdmin` 校验顺序把「已是其他社区管理员」误报为「未通过实名认证」；③ 加入 autoApprove 社区时前端一律显示「待审核」。修复：`AppTopbar.vue` 让平台管理员同时显示「平台管理」「社区管理」两个入口；`PlatformAdminView.vue` 任命改为从认证用户下拉选择并提示「重新登录后生效」；`PlatformService.appointAdmin` 调整校验顺序（先查本社区是否已有管理员 → 再查该用户是否已在别处任职 → 最后查实名认证）；`CommunityView.vue` 按后端返回 `JOINED/PENDING` 正确展示加入状态并加错误提示；`CommunityAdminView.vue` 审核加错误提示。演示库同时清理了历次测试产生的临时社区/用户/任命/申请与资金流水，恢复干净种子状态。
- **统一纠纷入口文案并补全演示账号**：订单页 `OrderDetailView.vue`、`OrdersView.vue` 中「发起纠纷 / 发现损坏 / 验收异常发起纠纷」等旧文案统一为「提出扣留押金」，与新纠纷流程术语一致；`README.md` 测试账号补 `shuling`（密码 123456，注册居民）并说明社区管理员为运行时任命产生。
- **配置库整理对齐配置管理计划**：`docs/` 重组为 RUP 四阶段目录（01-inception / 02-elaboration / 03-construction / 04-transition）；文档重命名为「阶段编号-中文名」（`01-开发职责说明.md`、`02-软件需求规范.md`、`02-界面原型.md`、`03-基线记录与变更记录.md`、`03-配置管理计划.docx` 等）；4 个 .md 补齐文档信息 / 修订历史 / 版本与基线标识，新增 `docs/README.md` 配置库索引；修正基线记录中 3 个过期 tag 提交号与开发职责说明的过时目录引用；各 .docx 补修订历史记录表与所属基线。
